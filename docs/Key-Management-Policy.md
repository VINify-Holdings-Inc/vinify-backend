## 1. Purpose & Scope

VINify uses **AWS Key Management Service (KMS)** as its sole, centralized cryptographic key management system. There is no separate, independently-managed key store or on-premises HSM — every encryption key protecting VINify data is a KMS key, verified directly via `aws kms list-keys` against the production account (8 keys total).

## 2. Key Generation

All keys are generated by AWS KMS, which uses FIPS 140-2 validated hardware security modules and NIST-standard algorithms (AES-256) with a cryptographically secure random number generator — this is AWS's own infrastructure and compliance attestation (FIPS 140-2, SOC reports), not something VINify independently re-implements or re-verifies at the algorithm level.

**Being precise about scope**: KMS keys don't have a custom "activation/deactivation schedule" beyond AWS's standard key lifecycle (a key is enabled on creation and can be disabled or scheduled for deletion on demand — Section 6). VINify has not defined a schedule beyond that standard capability.

## 4. Application-Layer / Field-Level Encryption

**Being direct: this does not exist today.** All eight keys above are infrastructure-level — they protect whole volumes, whole database instances, or whole services (RDS storage, EBS volumes, Secrets Manager, backups, ACM, SNS, CloudTrail, WAF logs). None of them, and nothing else in the application, applies field-level encryption or tokenization to specific sensitive columns (e.g., VIN data, PII) independent of that infrastructure-level protection.

There is an `encryptPayload`/`decryptPayload` helper (AES-256-CBC) in `src/helpers/utils.ts`, unit-tested, but verified via a direct codebase search to be called nowhere in the application — it is dead capability, not an active control. Sensitive data's only protection today is RDS's whole-disk encryption at rest and TLS in transit; there is no defense-in-depth if that outer layer were ever bypassed (e.g., via a compromised database credential, which would expose plaintext for every row). Introducing real field-level encryption for the highest-sensitivity columns (see [Data-Governance-and-Classification-Policy.md](Data-Governance-and-Classification-Policy.md) for what's classified Restricted) is open, real, unscheduled work — not claimed as done.

## 5. Segregation of Duties

For the six AWS-managed keys, AWS itself controls key lifecycle management entirely — no VINify individual has the ability to directly manage these keys' material or policy, which is the strongest possible separation between key management and data access.

For the two customer-managed keys (`alias/vin` and `alias/WAF`), key administration and routine engineering/data access are separated through IAM Identity Center:

- Betty's standing identity (`Betty-Daily`) has `Engineering-Daily`, a one-hour permission set with no KMS-administration permissions. A live negative test on 2026-08-15 confirmed that `kms:PutKeyPolicy` on `alias/vin` returns `AccessDenied`.
- Bethanie Nonami has the one-hour `KMS-Key-Administrator` permission set. It permits lifecycle and policy administration only for `alias/vin` and `alias/WAF` and contains an explicit deny for `Encrypt`, `Decrypt`, `ReEncrypt*`, `GenerateDataKey*`, signing, MAC, and shared-secret operations.
- Bethanie's former standing `SystemAdministrator` assignment was removed. `SystemAdministrator` is assigned only to the `AWS-Elevated-Admin-JIT` group, which has no permanent members.
- Betty's obsolete assumed-role principal with explicit `kms:*` was removed from the `alias/vin` key policy. Both customer-managed key policies now retain only the account-root IAM delegation and the AWS service statements required by their consumers.

Exceptional full administration uses the documented JIT workflow: a grant is time-bounded, logged, automatically revoked, and tied to an approval or emergency reference. The emergency path is capped at 60 minutes and requires retrospective review by Bethanie. The workflow was tested during this remediation with reference `ENC04-JIT-TEST-2026-08-15`; the grant succeeded, Betty's daily role remained unable to administer KMS, and automatic group-membership removal was scheduled and verified.

## 6. Key Distribution, Monitoring & Review

Every KMS action (key creation, policy change, rotation, enable/disable, deletion) is recorded by AWS CloudTrail (`vinify-audit-trail`, multi-region, always logging) with the identity, source, and timestamp of the action — see [AWS-Security-Setup-Guide.md](AWS-Security-Setup-Guide.md) Section 4. This is a real, existing, already-verified audit trail, not something built for this document.

A KMS policy change, key creation, or key deletion is itself a "modification to AWS infrastructure or security controls" under [Change-Management-Policy.md](Change-Management-Policy.md) Section 2's definition of a significant change — so it is documented and (where a second reviewer is available) reviewed through that same general change-management process, rather than needing a separate, KMS-specific approval workflow. There is no *additional* KMS-only review step beyond that.

## 7. Key Use, Crypto Period & On-Demand Rotation

Every key's defined cryptoperiod is 1 year (AWS KMS's standard automatic rotation interval), verified directly against each key above. Keys can be rotated or replaced on demand at any time, independent of the scheduled rotation, via `aws kms disable-key` (immediate deactivation) or by generating a new key and re-pointing the protected resource at it.

**Tested 2026-08-10.** The manual replacement path was dry-run end-to-end using two disposable test keys and a disposable Secrets Manager secret (never a production key or resource): created a secret encrypted under test Key A, verified it decrypted correctly, then re-pointed it at test Key B (`update-secret --kms-key-id`) and verified it still decrypted correctly under the new key with no data loss or downtime. Both test keys and the secret were then disposed of. This confirms the claim above is a proven capability, not just a theoretical one.

**Why 1 year**: this cryptoperiod was evaluated against VINify's actual disclosure risk and regulatory context, not just accepted as a default. The data these keys protect (RDS storage, backups, secrets, audit logs) is high-value but not subject to a specific external mandate requiring a shorter rotation interval — DPPA/NMVTIS (see [Data-Governance-and-Classification-Policy.md](Data-Governance-and-Classification-Policy.md)) governs permitted *use and retention* of VIN data, not key rotation frequency. Given that, and given the on-demand rotation capability above as a compensating control for any suspected exposure, the 1-year interval is judged appropriate rather than a compliance minimum being treated as sufficient by default. This judgment should be revisited if VINify becomes subject to a regulatory regime that specifies its own key-rotation requirement.

## 8. Production / Non-Production Key Separation

**Not currently applicable**: VINify operates a single production AWS account with no separate non-production environment provisioning its own KMS-encrypted resources today. There is no cross-environment key reuse because there is no separate non-production environment to reuse a key with. This section should be revisited if/when a staging or development environment with its own encrypted resources is introduced, to confirm distinct keys are used.

## 9. Key Accounting

Every key access — administrative (policy changes, rotation, enable/disable) and consumer (`Encrypt`, `Decrypt`, `GenerateDataKey` calls made by RDS, Secrets Manager, S3, etc. on VINify's behalf) — is a standard AWS KMS API call, and all KMS API calls are recorded as CloudTrail management events by default (not requiring opt-in data-event logging, unlike S3/Lambda).

**Being precise about exactly what's captured**: each log entry includes the calling identity (user/role), the specific action (`Encrypt`, `Decrypt`, `DisableKey`, etc.), the key ARN, and the timestamp. What it does *not* include: the specific downstream plaintext data that was encrypted/decrypted (KMS and CloudTrail only ever see ciphertext and key metadata, never the protected content itself, by design) or a resource-utilization metric. For the application-level question of *which record* a given decrypt call was for, that traces through the application's own request logs, not KMS's.

## 10. Key Destruction

AWS KMS provides both `disable-key` (immediate, reversible deactivation — a key can be taken offline the moment a compromise is suspected, with zero waiting period) and `schedule-key-deletion` (permanent destruction, with a mandatory 7-30 day waiting period as a safety margin against accidental deletion). This is the defined procedure for a compromised key or an offboarded individual with prior key-management access.

**Tested 2026-08-08.** No real key compromise or personnel departure has occurred, but the procedure itself was dry-run end-to-end against a disposable, purpose-created test key (never attached to any production resource, to avoid any risk to `alias/vin` or `alias/WAF`'s live consumers):
1. `disable-key` (compromise response) — verified immediate effect (`KeyState: Disabled`).
2. `enable-key` (recovery) — verified restoration (`KeyState: Enabled`).
3. `schedule-key-deletion` (personnel-departure permanent decommission) — verified the mandatory 7-day safety window is actually enforced (`KeyState: PendingDeletion`, concrete deletion date returned).
4. `cancel-key-deletion` (safety-margin cancel path) — verified it actually restores the key rather than being a theoretical option.

All four steps behaved exactly as documented above. The test key was then disposed of via the same `schedule-key-deletion` path, since it was never needed beyond this test.

## 11. Review Cadence

Reviewed whenever the key inventory changes (a new key created, a key's purpose changes) and at minimum annually. Each review is recorded as a new version-history entry above.
